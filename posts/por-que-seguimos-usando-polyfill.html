¿Por qué seguimos usando Polyfill?

Hace unos días estuve revisando un sitio web algo cuestionable. Por una parte, era un sitio totalmente estático usando NextJS, y no entendía para qué cargar tantos chunks de JavaScript por un sitio estático que perfectamente podrías hacer con Astro. Pero a pesar de ello, seguí revisando la página y me di cuenta de que usaba varios Polyfills. Y entonces me hice la pregunta: ¿por qué seguimos usando Polyfill hoy en día?

De dónde surge Polyfill

El término "polyfill" nace en el 2009 por Remy Sharp, aunque el servicio polyfill.io nació en 2014 por Andrew Betts. En su día, la fragmentación de los navegadores era máxima. Coexistían muchos motores de navegador distintos y, para resolver compatibilidades, era necesario implementar las nuevas funcionalidades de JavaScript a mano y ponerlo en el sitio web. De esta manera, Polyfills como String.prototype.trim() se implementarían en un script como: 

if (!String.prototype.trim) {
    String.prototype.trim = function () {
        return this.replace(/^[\s\uFEFF\xA0]+|[\s\uFEFF\xA0]+$/g, "");
    };
}

Para la época, esto solucionaba problemas de compatibilidad y permitía tener implementadas funciones que todavía no habían llegado al navegador. Sin embargo, esto tiene varios problemas claros: se está cargando JavaScript que en ocasiones es innecesario, y dicho JavaScript podría ser malicioso. Y eso fue exactamente lo que acabó ocurriendo.

El ataque de cadena de suministro

En febrero de 2024 Funnull, un CDN chino, compró el dominio polyfill.io y la cuenta de GitHub original. El creador original lanzó una advertencia pública: «remove it IMMEDIATELY».

El CDN había sido comprometido, y estaba inyectando código malicioso, de manera que los que estaban utilizando Polyfill tenían código malicioso corriendo en sus sitios web. Más de 100.000 sitios web fueron comprometidos en todo el mundo.

El código malicioso generalmente apuntaba a dispositivos móviles, y redirigía a sitios de estafa.

Sin embargo, cabe aclarar que el término polyfill lo usamos para referirnos a ese código que implementa una funcionalidad de JavaScript, por lo que no es una marca ni han sido todos ellos vulnerados.

El uso de Polyfill en 2026

Hoy en día, el uso de polyfills es cada vez más escaso. Y no es para menos; los navegadores ya no están tan fragmentados, y generalmente que una función nueva llegue a JavaScript es sólo cuestión de unas semanas que llegue también a la gran mayoría de navegadores.

Para casos especiales, como querer asegurar compatibilidad con navegadores antiguos, aún podría tener su utilidad, pero personalmente creo que para eso se podría usar el backend. Y en caso de funciones muy sencillas, como String.prototype.trim(), incluso se podrían añadir al propio código del cliente y mantener sin problemas.

Sin embargo, y aunque estas páginas que usen polyfills están seguras porque no llaman a polyfill.io sino que cargan el código localmente, ¿realmente son necesarios en 2026?

En mi caso concreto, aquel sitio web que estuve revisando era un estudio de videojuegos. El sitio es realmente sencillo: muy cargado de CSS pero sin nada de funcionalidad real. La única interacción que había era un formulario de contacto. Y sin embargo, el sitio cargaba 7 polyfills:

  • Array.prototype.at()
  • Array.prototype.flat()
  • Array.prototype.flatMap()
  • Object.fromEntries()
  • Object.hasOwn()
  • String.prototype.trimEnd()
  • String.prototype.trimStart()

PageSpeed categoriza estos polyfill como «Legacy JavaScript», y menciona que no son necesarios para los navegadores modernos y podrían eliminarse sin problema. No sólo eso, estos polyfill que prácticamente nadie está usando realmente al visitar este sitio, los sirve NextJS, por lo que los dueños de este sitio sufren el riesgo de que ocurra otro ataque de cadena de suministro y vulneren su página.

Mi conclusión

Sinceramente, creo que el uso de polyfills debe acabar lo antes posible. La mayoría de navegadores modernos ya no necesitan estas técnicas, y además reduces el rendimiento del sitio y aumentas la superficie de ataque. Y lo peor de todo es que esto me lo he encontrado en un sitio web totalmente estático, donde se podría incluso mover parte de estas funcionalidades a un backend, o implementar funciones de formateo triviales como String.prototype.trim o Array.prototype.at en un par de líneas de JavaScript, pero no proporcionado por un tercero.

Si tu sitio web utiliza polyfills, por favor revisa si acaso es necesario hacerlo, y dejemos de complicar la web.
